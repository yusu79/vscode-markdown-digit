# Out-of-Code Insights

このプロジェクトでは、ソースコードを汚さずに実装意図・設計上の判断・注意事項・作業上の論点を共有するため、Out-of-Code Insights の annotation を使用する。

## 基本方針

* 作業開始前に未解決の annotation を確認する
* 変更対象のコードに関連する annotation がある場合は、ファイルを変更する前に内容を確認する
* annotation の指示・質問・注意事項は作業時のコンテキストとして扱う
* annotation だけで判断せず、必要に応じて実際のコード・テスト・仕様と照合する
* 実装理由や設計判断など、ソースコードの可読性に不要な説明コメントは、必要に応じて annotation として残す
* コード自体の理解に不可欠なコメントはソースコード内に記述してよい

## パスと行番号

複数フォルダーの VS Code ワークスペースでは、MCPのワークスペースルートと annotation の相対パスが一致せず、行番号が `-1` になる場合がある。

`line: -1` でも annotation 自体が無効とは判断しない。

`fileUri`、ワークスペース構成、実際のファイルを確認して対象を特定する。

行番号を解決できない場合は、推測だけで対象コードを決定しない。

## annotation の追加

将来の作業で参照する価値がある情報を annotation として残す。

例:

* 実装から分かりにくい設計判断とその理由
* 意図的に採用しなかった実装方法とその理由
* 将来変更するときに注意すべき制約
* ユーザーへの確認が必要な論点
* 後続作業へ引き継ぐ必要がある情報

単なる変更内容の要約や、コードを読めば明らかな内容は残さない。

## annotation への対応

* 質問や指示がある場合は、利用可能な機能の範囲で回答または対応する
* 必要に応じて対応内容を記録する
* 対応完了後は削除せず Resolved にする
* 未対応の annotation を勝手に Resolved にしない
* 対象コードとの対応関係が不明な場合は、推測で別のコードへ関連付けない

## MCPからの操作

利用可能であれば `out_of_code_insights` MCP Server の専用ツールを使用する。

新しいセッションでは、作業開始時に `list_annotations` を使用して未解決 annotation を確認する。

MCPの利用可否を確認する目的だけでテスト annotation を作成しない。

MCPが利用可能な場合は、annotation の保存ファイルを直接編集せず、専用ツールを使用する。

annotation の追加・更新・Resolved化・削除などの状態変更は、実際の作業で必要な場合だけ行う。

MCP Server が利用できない場合は、その旨を報告する。

annotation を直接確認する必要がある場合は、現在のプロジェクトディレクトリだけを前提にせず、VS Code ワークスペース内の `.out-of-code-insights/annotations.json` を確認する。

保存場所が分からない場合は推測したパスを使わず、ワークスペース内から `.out-of-code-insights/annotations.json` を検索する。
